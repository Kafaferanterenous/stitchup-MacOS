PRODUCT GOAL

Build Stitchup, a fast offline-first PDF viewer/editor with a familiar desktop
layout inspired by common PDF applications, but with independently designed
visuals. The target is broad useful coverage, portability, and safe output, not
an unsafe claim of full Acrobat compatibility.

Core goals:

- open and render ordinary PDFs reliably;
- page thumbnails, search, zoom, fit modes, and text selection;
- reorder, rotate, delete, insert, split, merge, and extract pages;
- edit metadata and save-as safely;
- add non-destructive text boxes, highlights, shapes, ink, images, stamps,
  and visual signatures;
- fill existing AcroForms;
- export a new PDF without destroying the source;
- provide clear status, undo, cancellation, and recovery behavior;
- run offline without accounts, telemetry, or cloud services.

ARCHITECTURE

Use layers and narrow interfaces:

1. Document model: pages, metadata, object references, permissions, source
   hash, and non-destructive operation history.
2. Renderer adapter: PDF.js or a native renderer, selected only after a size,
   startup, quality, and license experiment.
3. Structure adapter: page tree operations, metadata, forms, attachments,
   validation, and save-as.
4. Overlay layer: text boxes, annotations, shapes, ink, stamps, images, and
   signature appearances.
5. Commit/export layer: generate a new PDF, preserve the source, write to a
   temporary file, validate, then atomically publish.
6. Optional providers: OCR, QPDF structural operations, cryptographic
   signatures, compression, and local AI.

Do not make the GUI depend directly on a particular PDF engine. Do not put
filesystem writes or long PDF operations on the UI thread.

IMPORTANT PDF LIMITATIONS

PDF text is positioned drawing content, not normal flowing document text.
Do not begin by pretending arbitrary click-to-edit/reflow is solved. Stage 1
and Stage 2 should use overlay text boxes and preserve original content. Add
limited original-text replacement only after proving font metrics, encoding,
clipping, line geometry, and save/reopen behavior with fixtures.

RECOMMENDED IMPLEMENTATION STAGES

Stage 0: design and legal ledger

- write the document model and engine interfaces;
- define a dependency/provenance ledger;
- define source-preservation and atomic-save rules;
- define sanitized fixture PDFs and acceptance tests;
- choose a project license only after dependency review.

Stage 1: viewer and page workspace

- open PDF and render pages;
- continuous/single-page view, thumbnails, zoom, fit, search, text selection;
- page reorder, rotate, delete, insert blank page, split, merge, extract;
- metadata view/edit;
- open/save-as with source preservation;
- undo for page operations;
- dark, blue, and high-contrast themes with readable font scaling.

Stage 2: safe authoring overlays

- text boxes and free text overlays;
- highlight, underline, strikeout, shapes, arrows, freehand ink;
- image and stamp placement;
- visual signature appearance, clearly distinguished from cryptographic signing;
- fill existing AcroForms;
- explicit flatten-overlays export.

Stage 3: security-sensitive features

- redaction that removes underlying text/images from the output object graph;
- redact preview followed by search/stream/visual verification;
- encryption/password handling through a reviewed engine;
- cryptographic signatures using a documented CMS/PKCS#7/X.509 design;
- warn that any post-sign edit invalidates signatures;
- PDF/A validation as an evidence-backed report.

Stage 4: optional providers

- OCR with separately licensed language data;
- compression and image downsampling profiles;
- Bates numbering;
- local AI summary/extraction only through an explicit local provider and
  privacy setting.

INTERFACE

Use a familiar, independently designed desktop layout:

- top command/ribbon area: Open, Save As, Undo, page operations, annotate,
  forms, redact, sign, export, and search;
- left thumbnail/navigation pane;
- center page canvas;
- right properties/tool pane;
- bottom page/zoom/status bar;
- keyboard shortcuts, command search, accessible focus order, visible errors.

Do not copy PDF Gear or Nitro Pro logos, icons, wording, exact dimensions, or
distinctive artwork. Common toolbar concepts are not owned by one vendor.

PORTABILITY OPTIONS

Track A, fast prototype: Rust core plus Tauri/PDF.js frontend. This is
cross-platform and productive, but depends on a system WebView and ships
JavaScript assets. Measure clean-machine behavior and do not call it fully
self-contained if it needs a WebView runtime.

Track B, strict native package: Rust or C++ native UI plus a measured native
renderer/backend. This can produce a smaller Windows ZIP but requires more UI
work. Keep platform code behind adapters.

Do not choose a framework by popularity. Measure startup time, idle memory,
large-document memory, package size, rendering fidelity, and clean-machine
launch before deciding.

SECURITY AND DATA SAFETY

- Never overwrite the source PDF by default.
- Use temporary files and atomic publication.
- Preserve source hash and operation history.
- Treat embedded files, JavaScript, links, forms, and external references as
  untrusted content.
- Make active content policies explicit and default to safe behavior.
- Do not send PDFs to a server or cloud service.
- Do not include private PDFs, real names, signatures, or credentials in tests,
  logs, screenshots, or fixtures.
- Redaction must be tested against hidden text, alternate content streams,
  images, metadata, attachments, incremental revisions, and copy/search.

TESTING

Create sanitized fixtures for:

- text, scanned image, mixed text/image, rotated pages, forms, annotations,
  embedded fonts, Unicode, encrypted PDFs, malformed PDFs, attachments,
  incremental updates, and large page counts.

Test:

- render/open/save-as round trips;
- page order and geometry;
- overlay placement after zoom/rotation;
- undo and crash recovery;
- redaction content removal;
- signature invalidation warnings;
- output validation and atomic failure behavior;
- cold/warm startup, idle memory, large-document memory, and package size.

Do not run GUI visual tests or live external integrations without explicit
authorization. Static checks are not live acceptance.
